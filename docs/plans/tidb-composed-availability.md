# Plan: composed TiDB request availability

Status: deterministic joint-replay and sampled-candidate ILP pilot implemented 2026-11-12; calibrated TiDB-wide stochastic model and realistic-scale optimization remain open. Builds on `docs/plans/tidb-write-availability-dependencies.md` and the local PD-outage experiment in `outputs/tidb/local-pd-dependency-20261111.json`. No cloud experiment was run.

## Define the two metrics first

Fix a finite set of supported *data-plane* request classes `Q` (at minimum normal autocommit write, fresh scan, point get, and an explicit old-snapshot read). Record constant SQL and metadata queries as separate diagnostics. DDL, administrative operations, and arbitrary multi-partition transaction graphs require their own scope definition; do not silently claim every possible SQL statement. A request is successful only if it finishes within the experiment's 5 s client deadline. Existing causal 1PC transactions can survive a PD outage briefly, but **full functionality** still fails if a normal write or fresh scan fails.

For shard `i`, class `q`, client region `r`, event trace `ω`, and request start time `t`, let `S[i,q,r](t,ω)` be 1 if that request returns a valid result by `t+5 s` (not merely if its TiKV Region has quorum). Set `F[i,r](t,ω) = min_{q∈Q} S[i,q,r](t,ω)`; this is *all supported request types work on one partition*. If the SLA requires clients in **every** region, take a minimum over `r` too; otherwise specify a representative/client-weighted region. Keep an explicit request mix for the observed workload metric, which is different from this all-classes metric.

- **Single-access partition availability:** `A_i = E[∫ F[i](t,ω) dt / H]`; report every shard and a declared workload-weighted `A_single = Σ_i w_i A_i` (`Σ_i w_i=1`). A uniform `w_i=1/N` describes a uniformly chosen partition, **not** all partitions being available. If “single access” instead means *any one of the 300 partitions is usable*, use `E[∫ max_i F[i](t,ω) dt / H]`; this is a different, much weaker service guarantee and should not be substituted silently.
- **Full-access partition availability:** `A_full = E[∫ min_i F[i](t,ω) dt / H]`. One failing partition or a shared PD/TSO/schema outage makes this predicate false. Record both metrics on the *same runs*. A concurrent multi-partition transaction can have additional coordination failures not captured by a conjunction of independent single-partition requests; test or model these separately before claiming a universal transaction SLA.

For intuition with 300 otherwise healthy partitions and no overlapping failures: a PD outage of duration `d` reduces **both** metrics by `d/H`, not `300d/H`; a failure of one partition for `d` reduces uniform `A_single` by `d/(300H)` but `A_full` by `d/H`. Consequently `A_full ≤ A_i` for every `i`, and `A_full ≤ A_single`.

The per-partition `can_commit` metric and the optional episode statistic (`rust/powder-mc/src/sim/metrics.rs`) remain diagnostics. `sum(max(d−T,0))` is not automatically 5 s request success or 45 s schema validity. In the local v8.5.8 test, normal fresh scans and autocommit writes timed out during a full single-PD outage, while point gets and cached/old-snapshot scans continued. Thus PD/TSO is a shared gate on the **all-classes** predicate, not a blanket gate on every request class.

## Joint simulator changes

1. **Fleet state and one clock.** Extend the Rust MC job from one RSM (`rust/powder-mc/src/config.rs:319-341`) to a deployment of named shard placements, PD members, TiDB frontends and system-metadata TiKV stores/Regions. Run the shared region/global/AZ outage processes once per trajectory (`powder/faults/convert.py:176-216`); apply one physical-machine/process failure consistently to all replicas and services on that host. Preserve independent per-Region Raft/election state where appropriate. Reusing the same random seed for 300 separate existing jobs does **not** synchronize their generated fault traces.
2. **PD and schema state.** Track the actual PD member-to-region map (`powder/deploy/spec.py:335-350`), quorum, leader election and reachable TSO from the chosen TiDB frontend; pause PD-driven repair/placement while scheduling is unavailable, without disabling TiKV's own Region leader election. Track system-metadata Region quorums and each TiDB frontend's last successful schema refresh/expiry. When PD/TSO is already down, a later schema expiry is an overlapping cause, not extra downtime. Keep the 5 s client deadline, ~45 s default schema lease, PD election and store-repair timers independent and calibratable.
3. **Request predicates and timing.** On each shared event timeline, evaluate `S[i,q,r]` for supported classes using the request deadline and any retry/failover delay. Prefer actual request-start probes at representative times plus exact event/timeout boundary accounting over converting `can_commit` totals after the fact. Accumulate per-shard `A_i`, the weighted single-access value and `A_full` for the same trajectory. Also retain cause attribution: PD-only, schema-only, user-Region-only and overlap, without adding overlapping seconds. Report per-run values and uncertainty across trajectories; censor horizon-crossing requests explicitly.
4. **Calibration.** Compare by-class success and latency against the archived local PD probe and live TiDB workload/probe streams. Add a small 3-member local PD quorum/failover test before calibrating a PD downtime distribution; the one-member local experiment proves full-service loss behavior but not 3-member failover latency. Do not run a billable AWS deployment without explicit approval.

## Placement ILP changes

The existing fleet model selects candidate counts and minimizes **sum of candidate unavailability** under unique-machine billing (`powder/faults/gurobi_ilp.py:38-96`); the named-shard variant has `x[i,c]` but still minimizes that sum (`powder/faults/gurobi_ilp.py:99-194`). Both are additive *single-access* objectives, not exact `A_full` objectives. Keep machine costs, replica capacity, transfer and migration constraints from the existing ILP.

**Single-access objective:** Use candidate scores from the *joint* traces: `a[i,c]=E[F_i | shard i chooses candidate c]`, including PD/TSO, schema and correlated regional faults. Minimize `Σ_i w_i(1−a[i,c])x[i,c]`. If control-plane behavior depends on the other selected placements (shared load, scheduler contention or physical-host choices), this candidate coefficient is only a surrogate; evaluate the whole selected deployment exactly. A shared PD failure enters each `a[i,c]`, but because `Σ w_i=1`, it is not multiplied by the shard count in the **reported** `A_single`.

**Full-access objective is coupled:** For a finite set of weighted shared trajectories/time intervals `s`, precompute `g_s=1` if global PD/schema/frontend predicates allow all required request classes, and `b[s,i,c]=1` if shard `i` on candidate `c` serves every required class in interval `s` under that *same* trace. Add binary `z_s` with `z_s ≤ g_s` and `z_s ≤ Σ_c b[s,i,c]x[i,c]` for each shard `i`; maximize `Σ_s weight_s z_s` (or require it above an SLA floor and minimize all-in cost). For fixed selected `x`, maximizing `z_s` makes it the AND of global and all shard-success predicates. Intervals should split at event, schema-expiry and 5 s request-deadline boundaries; weights are durations, not arbitrary independent samples. Recompute/validate `b` if placement choices alter the shared dynamics.

This sampled full objective can be very large (`N × candidate arcs × timeline intervals`), so start with small `N`. At ~300 shards use a **staged candidate-menu approach**: optimize the linear single-access surrogate, run a joint fleet MC evaluation on the selected deployment, and perform budget-feasible neighborhood/column improvements using common scenarios. An optional compact scenario MILP or iterative critical-failure cuts can refine `A_full` if the pilot scales. Always validate on held-out trajectories with uncertainty; a sampled menu optimum is not a global reliability guarantee.

**Safe linear diagnostic:** With `G` the shared global predicate and `R_i` each local predicate, the failure union satisfies

`P(¬G ∪ ⋃_i ¬R_i) = P(¬G) + P(G ∧ ⋃_i ¬R_i) ≤ P(¬G) + Σ_i P(G ∧ ¬R_i)`.

The right side is an *upper bound on full unavailability*, useful as a linear surrogate or conservative constraint, not an exact full-access availability. It counts PD failure once. Multiplying per-shard marginal availabilities assumes independence and is wrong when the same PD, region or host affects several shards; summing already-composed per-shard unavailabilities counts a shared PD outage up to `N` times.

## Validation gates

- Analytic toy timelines: (a) global PD outage with every user Region healthy gives all `A_i=A_full=A_PD`; (b) one shard down only affects that shard but drops `A_full`; (c) two shards down concurrently contributes the union once; (d) region failure simultaneously takes out one PD member and user replicas; (e) outage below a 5 s request deadline vs above it; (f) schema lease expires while PD stays reachable.
- Compare `A_single`, `A_full`, per-shard counts and cause overlap against brute-force enumeration for 2–3 shards; add a 300-shard memory/runtime benchmark before broad sweeps.
- Preserve old one-RSM MC/job and legacy ILP outputs when new mode is off. Set separate quality floors for mean per-partition and full-access availability; an `A_full` target cannot exceed the availability of its shared global services.

## Implementation status and limits (2026-11-12)

- [x] Opt-in Rust `mode=joint` deterministic event replay (`rust/powder-mc/src/sim/joint.rs`), separate from legacy single-RSM jobs. A whole fleet shares one host/region/AZ/global toggle timeline; explicit three-member PD quorum/leader failover, system-metadata quorum/schema lease, selected TiDB frontend and four supported request classes feed request-start masks with a deadline. Requests starting in the last deadline interval are censored. The output reports per-shard, uniform single-access, full-access and per-class fractions, plus candidate masks. **This is an abstract dependency replay:** zero service time, no real Raft log state, network partitions, automatic replica repair, PD scheduler, arbitrary TiDB transactions or frontend failover.
- [x] `powder/faults/joint_trace.py` adapts the fault library's reproducible physical-slot/region/global traces into unioned toggles and adds AZ fault streams, without drawing the same physical host's fault separately for each shard. Permanent events remain down through the horizon because this pilot has **no repair**. `sample_joint_replays` repeats independent whole-fleet seeds and concatenates candidate masks from complete trajectories; it does not supply a statistically validated rare-event CI.
- [x] `powder/faults/composed_availability.py` evaluates per-shard, weighted single-access and full-access availability on a shared timeline. `solve_transition_gurobi(..., composed=timeline, composed_objective="single"|"full")` adds both objective modes and optional separate quality floors while retaining unique-machine billing, capacity, replication traffic, migration and replica-move constraints. A Gurobi scenario binary represents each interval's all-shards-accessible outcome; an old per-RSM MC estimate is **not** substituted for missing joint candidate masks. Lattice ascent is skipped in this mode until neighbors are jointly scored.
- [x] Deterministic toy tests: shared PD outage counted once, one failing shard versus the full-fleet AND, overlapping outages, schema lease, deadline, physical host/region event, cost/movement constraints and differing ILP choices for single versus full. Rust library suite: 210 passed; Python focused composed/joint tests passed. A release-engine seeded two-draw 30-day toy ran end to end (its exact outcomes happened to be all 1.0, so this is a wiring check, **not** evidence of 100% TiDB availability). A **synthetic** 300-shard/two-candidate/7-interval replay and full ILP solved optimally in ~0.008 s and ~0.178 s respectively; this does not benchmark a realistic candidate menu, detailed fault model or target nines.
- [ ] Complete the calibrated stochastic **joint** Rust simulator: native shared hazard draws or validated externally generated traces at realistic menu sizes, true TiKV Raft/election and PD-conditioned repair, TiDB TSO/client routing, schema refresh phases, request latency/retry semantics, correlated physical host load, and statistical validation against real traces/held-out deployments. Until then, label all composed results **deterministic/no-repair pilot estimates**, not paper-ready TiDB availability.
