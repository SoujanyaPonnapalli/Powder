# Plan: Operating and transition costs for RSM placement

Status: opt-in implementation and local validation completed 2026-11-11; large-scale benchmark remains open. Scope: a cost-aware extension of the existing fleet placement and reconfiguration pipeline, not a replacement for exec #6's later storage-capacity and GB-movement frontier. No cloud deployment is part of this plan.

## Assessment

**Reasonable, but not a single cost-coefficient change.** Running transfer is a precomputable cost per candidate. Migration is a one-time, shard-dependent cost relative to an old deployment, and a placement-change limit requires the optimizer to know which old shard becomes which new shard. The current fleet ILP counts interchangeable placement shapes; the cadence runner computes migration only *after* choosing them. The work is a moderate extension to pricing and a substantive change to the selection model. Start with small, exact, named-shard solves and keep the current homogeneous-count path as a compatibility and scaling baseline.

## Decision contract and units

1. **Shard records.** Introduce an optional, versioned workload input with stable `shard_id`, `write_gb_per_s` (nonnegative, decimal GB/s), and `partition_gb` (nonnegative, decimal GB). A shard's old placement is a set of physical machine IDs, not a machine class. If all shards truly share these parameters and identities do not matter, identical old-placement/workload groups can be aggregated. Do not silently permute named or heterogeneous shards. The existing list-of-placements input continues to work in legacy runs.
2. **Traffic convention.** Treat `write_gb_per_s` as the leader's rate to *each* follower (one copy per follower), with no assumption about which replica is leader. For a candidate with `k` replicas, compute its advertised average directed-edge price

   `q(P) = sum_{u != v in P} transfer(u -> v) / [k (k - 1)]`  ($/GB).

   Then its expected running transfer charge is `3600 * write_gb_per_s * (k - 1) * q(P)` ($/h). This is the uniform-leader approximation: each node leads 1/k of the time. Use directed AWS regional prices, including the existing inter-AZ price for traffic between AZs in one region, and zero for same-AZ traffic. If the user's GB/s measurement is instead total outbound replication across *all* followers, remove `(k - 1)` and name the input accordingly. Document the uniform-leader assumption; do not imply it is a measured leadership distribution.
3. **Migration policy.** For each newly added machine `m` in shard `s`, copy one partition from the cheapest eligible old replica `u` of that same shard: `partition_gb[s] * min_u migration_price(region(u), region(m))`. Retained machine IDs move nothing. **Any same-region copy is free in this requested model, even if AZs differ**; for a cross-region copy, use the library's directed inter-region $/GB once (the AWS table says inter-region egress is billed at the source). Do not add an invented ingress fee or reuse `transfer_per_gb(..., same_az=False)` for same-region migration: that helper currently bills inter-AZ traffic. Report GB copied even when its modeled charge is zero. If no old replica can serve as a source, fail explicitly or handle a separately specified recovery path; never give that move a free price.
4. **Movement limit.** Count changed **shard-to-machine assignments**: `moves = sum_s |new[s] \ old[s]|`. A replica placed on a machine already used by another shard counts exactly the same as one placed on a previously unused machine. One 3-to-5 expansion uses two moves. Expose `max_replica_moves=K`; zero means no additions. Report replica removals separately, but do not introduce an activated-versus-existing-machine distinction or a second machine-churn constraint for this study.
5. **One-time versus recurring dollars.** With an explicit decision horizon `H > 0` hours, use `operating_per_hour = sum_m machine_price[m] * active[m] + sum_s running_transfer_per_hour[s,new[s]]`, `migration_usd = sum_s migration_usd[s,old[s],new[s]]`, `total_usd = H * operating_per_hour + migration_usd`, and `effective_per_hour = total_usd / H`. Only `effective_per_hour` can be compared to the existing $/h budget. A machine used by the new configuration has the same $/h price whether or not it appeared in the old configuration; there is no activation surcharge. Report the three cost components separately. A longer horizon changes whether a move pays for itself; never add raw migration dollars to a dollar-per-hour budget. Without a specified old deployment, migration is not charged; reject a movement cap without an old deployment.
6. **Optimization semantics.** Preserve the existing maximize-availability-under-budget problem when no new inputs are supplied. In the transition-aware variant, constrain all-in `effective_per_hour <= budget_per_hour` and `moves <= K`; for cost optimization under an availability floor minimize `total_usd` (equivalently `effective_per_hour`). For the existing near-max-availability tie-break, hold quality within its stated tolerance, then minimize the same all-in total. A transfer cost included only in the returned report does *not* change an availability-maximizing choice unless it also affects its budget, a hard constraint, or that tie-break. Retain the old deployment as an available, exact-scored feasible column when its machines are available and it meets current constraints.

**Magnitude check:** 1 GB/s per follower at 3 replicas and $0.02/GB on each directed edge costs `3600 * 1 * 2 * 0.02 = $144/h` per shard. Moving a 100 GB partition over one $0.02/GB cross-region edge costs $2 once. State decimal GB versus GiB conversions in telemetry; these terms should not be combined without H.

## Implementation sequence

### A. Pure pricing and migration primitives

- Add an immutable-pinned transfer-price resolver around `data/fault_library/prices/aws-transfer.json` (`price-transfer/aws-us@2026-10-21`); reuse `powder/faults/prices.py`'s directed cross-region data, but distinguish replication traffic from the requested free-within-region migration policy. Validate full region coverage, finite/nonnegative rates and sizes, distinct machine IDs, and 0/negative horizon. No change to recorded source values or existing entries.
- In `powder/faults/reconfig.py`, add a pure per-shard transition-cost function accepting old and candidate machine sets, size, machine locations and source eligibility. Keep the existing `migration()` post-hoc API and its inter-AZ-billing behavior for historical cadence results; introduce explicit policy/version for the new path rather than silently rewriting past outputs. Return replica additions/removals, GB moved, and USD.
- Cache `q(P)` once per unique placement and `(old shard, destination machine)` cheapest-source prices for candidate arcs. Preserve exact candidate MC availability independently of cost.

### B. Transition-aware MILP in the production path

- Extend the unique-physical-machine Gurobi model at `powder/faults/gurobi_ilp.py` (called by `scripts/pilot_fleet_frontier.py`) with shard-aware `x[s,c]` (binary choice of candidate `c` for shard `s`), or group identical `(old placement, GB/s, partition GB)` shards into integer flow `z[group,c]`. Enforce one candidate per shard/group, the existing machine replica-capacity limits and `y[m]` activation, operating + amortized migration budget, and `sum additions <= K`. Existing availability coefficients remain candidate-based; costs and movement are shard/candidate-specific. Give unchanged old placement a valid zero-move arc. Keep the existing count-based solver untouched for legacy homogeneous experiments until parity tests pass.
- Avoid an all-pairs `N_shards × N_candidates` expansion at catalogue scale. Deduplicate old groups; prune candidate arcs whose moves individually exceed `K`; offer old placements, valid one/few-replica neighbors, and other bounded-cost promising columns. Mark results as candidate-menu optima, not global optima. Benchmark model size, incumbent availability, optimality gap and wall time on 10/50/100 shards before lifting the restriction. If using group flows, the constraints `sum_c z[g,c] = count[g]` and `sum_g z[g,c] = x[c]` preserve the existing candidate multiplicities and machine capacity. These flows must select the assignment; independently running the old overlap-maximizing Hungarian matcher afterward can give a *different* cost.

### C. Integrate every solve and report path

- Thread workload, old deployment, H, K and pinned transfer ID through `scripts/reconfig_cadence.py` and `scripts/pilot_fleet_frontier.py` without changing legacy defaults. Update fleet preselection (`powder/faults/fleets.py`), warm starts, exact-MC re-solves, lattice ascent and the cost tie-break to use the same all-in cost/movement guard; no later stage may replace a feasible solution with a cheaper-compute but invalid move. The current fleet knapsack uses a compute-only budget and a high budget-utilization lower bound; revise these heuristics so traffic can fit within the budget and the previous fleet can remain eligible.
- Extend outputs with machine $/h, replication $/h, migration USD, effective $/h, GB moved, replica moves, H, workload/price IDs, and infeasibility reason. Recalculate from the selected named-shard deployment and assert the MILP's accounting matches within tolerance. Continue to report availability separately; keep old output schemas/versioned runs reproducible and do not rewrite saved figure results.
- Run small off-cloud cadence examples first. Keep old post-hoc migration metrics as explicitly named legacy metrics or switch consumers with a versioned output field; never compare incompatible same-region policies without labeling them.

### D. Tests and validation gates

- Pure tests: directed asymmetry; RF 3/5/7 directed-edge average; same AZ zero traffic; inter-AZ replication charged but same-region migration free; cross-region cheapest of multiple old sources; retained machine zero move; 3-to-5 adds two; decimal GB/second to GB/hour and $/h; invalid price, negative size/rate or missing region fail.
- Solver toy cases: zero-move cap selects old configuration; positive K changes exactly K replica assignments whether destination machines were already in use or not; shared-machine capacity and machine price charged once, with no activation surcharge; differing shard write rates alter assignment; movement savings justify a switch only for sufficient H; strict budget can make a higher-availability candidate infeasible; identity preserved even when placement lists reorder; a local per-shard choice conflicts on capacity; tie-break and ascent retain feasibility. Check `K=0` and tight K infeasibility explicitly. Skip Gurobi tests where no license is available, and keep pure tests independently runnable.
- Regression: old parameters produce the old machine-only objective and selected results; migration dollars match independent per-shard post-selection accounting; old migration tests remain unchanged; benchmark sparse candidate menus against the existing solver, recording solve time and gap. Run no AWS deployments or multi-month sweeps as part of implementation.

## Future compatibility and scope boundaries

This plan does **not** implement exec #6's machine storage limits, maximum GB moved, minimum-Z availability frontier, or physical migration schedules. Expose per-shard partition sizes and `GB_moved` now so a later `sum_s partition_gb[s] * additions[s] <= Z` and `sum_s sum_{c: m in P_c} partition_gb[s] * x[s,c] <= storage_gb[m]` can be added without changing input identities. A zero-dollar same-region move still consumes bytes, slots and the K limit. The AWS transfer table is a price proxy for the paper's modeled machine classes, not proof of measured bills on heterogeneous hosts.

## Proposed order of work

1. Settle the remaining contract choices: whether GB/s is per follower or aggregate, the decision horizon H, and whether within-region migration should deliberately ignore inter-AZ billing. This plan now fixes K as the number of added shard-to-machine assignments, with no distinction between previously used and newly used machines. The other proposed defaults are **per follower, caller-supplied H, same-region free**.
2. Land versioned inputs and pure pricing/migration tests.
3. Land small-scale shard-aware ILP + accounting tests, preserving legacy solve behavior.
4. Connect fleet/cadence, exact-score re-solves, and ascent; run smoke cases and report benchmark size/gaps. Only after these gates consider a broader rerun or live use.
