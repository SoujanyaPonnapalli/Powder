# TiDB write availability: PD, schema metadata, and long outages

Status: research and implementation design, 2026-11-11. No change to the Monte Carlo availability definition yet. This note distinguishes observed behavior in the project's v8.5.8 live gate from documented general behavior; it does not claim an unmeasured outage threshold is exact.

## The three different failure paths

| Dependency | When a write can fail | Model implication |
|---|---|---|
| **User-data TiKV Region** | Its Raft leader cannot obtain a write quorum, or the client cannot reach a usable leader within its request deadline. TiKV runs its own Raft leader election; PD is not the Region's Raft leader. | Existing per-RSM `can_commit` and election-delay model; keep the 5 s application deadline distinct from the Raft election and node-replacement timeouts. |
| **PD timestamp/metadata service** | The standard deployment uses PD for transaction timestamps (TSO). If the PD service loses quorum or its TSO cannot be reached, new SQL transactions can wait or fail even if user-data Regions retain quorum. A single PD member failure need not do this if PD retains quorum; a PD leader change may cause a short client-visible stall. | A *shared* control-plane gate on SQL writes, requiring explicit PD membership, leader/TSO service and reachability. Do not use the Region Raft election timeout or PD's `schedule.max-store-down-time` as a TSO failure timeout. In PD microservice mode TSO and scheduling can be separate, but our TiUP topology starts regular PD servers and does not configure a separate TSO service. |
| **PD scheduling and TiDB schema/system data** | PD schedules new replicas and leader transfers from TiKV heartbeats; the Region leader performs reads/writes. Losing scheduling alone does not cancel an already-healthy Region quorum, but prevents or delays repair, balancing and placement changes, increasing exposure to subsequent failures. Separately, TiDB persists schema metadata under TiKV `m_` keys and uses PD's global schema-version key. If TiDB cannot load/validate fresh schema for a DDL lease, DML can fail with error 8027 (`Information schema is out of date`). The documented default lease is **45 s**. | Scheduler availability conditions *repair and placement transitions*, not an unconditional instant global-write gate. Track schema freshness per TiDB SQL server, tied to the availability of the specific metadata path; do not infer a universal dependency on every `mysql.*` table. |

### Which requests need a fresh TSO

Not all SQL requests fetch a timestamp from PD. Ordinary transactional writes obtain a start timestamp; the standard optimistic 2PC path also obtains a commit timestamp. With causal consistency and async/one-phase commit, the separate *commit-time* PD request can be avoided, not necessarily the transaction's start timestamp. Consistent reads commonly need a snapshot timestamp, but not every `SELECT` performs a fresh PD request: TiDB documents point-get/snapshot fast paths and an opt-in low-resolution cached TSO for read-only operations that tolerate staleness (`tidb_low_resolution_tso` is off by default). Explicit stale-read settings do not apply to DML. A constant-only SQL statement need not perform a TiKV data read, but its behavior during a complete PD outage has not been established by these sources. Model a PD/TSO outage as a shared dependency for *normal transactional writes*, not an assertion that every request instantly fails. Sources: [optimistic 2PC](https://docs.pingcap.com/tidb/stable/optimistic-transaction/), [transaction overview and causal consistency](https://docs.pingcap.com/tidb/stable/transaction-overview/), [latency breakdown](https://docs.pingcap.com/tidb/stable/latency-breakdown/), [read-only TSO cache](https://docs.pingcap.com/tidb/stable/system-variables/), [read staleness](https://docs.pingcap.com/tidb/stable/tidb-read-staleness/).

### How PD availability depends on the regions

The deployment's default **three PD members** are assigned round-robin starting in the control-plane region, then through the regions containing TiKV slots (`powder/deploy/spec.py:111-117,335-350`). With at least three distinct regions, the three PD members occupy three regions. With only two eligible regions, the assignment can be A–B–A: losing A kills two PD members and their quorum. Thus PD availability depends on the *actual member-to-region map*, not the number of regions in the experiment alone. A fourth region with no PD member can still lose user-data writes and its local SQL frontend, but its outage does not by itself remove PD quorum.

For an illustrative three-region A–B–C layout and independent whole-region up probabilities `p_A`, `p_B`, `p_C` (ignoring node-specific faults and network partitions), PD quorum availability is `p_A p_B + p_A p_C + p_B p_C - 2 p_A p_B p_C`; for equal `p`, this becomes `3p² - 2p³`. **This is not a valid shortcut for the experiment's end-to-end availability:** the library also has global/AZ outages (`powder/faults/convert.py:176-216`), PD nodes can fail individually, a network split can leave living PD nodes unable to form or reach a quorum, and the same regional event affects user-data replicas. A surviving quorum may still have a short PD-leader/TSO failover. The client needs a reachable TSO service, not just two powered-on PD instances. Simulate the shared outage event once, then evaluate PD/TSO, schema and user-RSM availability on that same timeline.

Sources: [TiKV Raft configuration](https://docs.pingcap.com/tidb/stable/tikv-configuration-file/), [TiDB scheduling](https://docs.pingcap.com/tidb/stable/tidb-scheduling/), [TSO](https://docs.pingcap.com/tidb/stable/tso/), [PD recovery](https://docs.pingcap.com/tidb/stable/pd-recover/), [PD microservices](https://docs.pingcap.com/tidb/stable/pd-microservices/), [TiDB metadata and global schema version](https://docs.pingcap.com/tidb/stable/tidb-computing/), [SQL FAQ: outdated schema](https://docs.pingcap.com/tidb/stable/sql-faq/#what-are-the-causes-of-the-information-schema-is-out-of-date-error), [PD configuration](https://docs.pingcap.com/tidb/stable/pd-configuration-file/), [TiDB configuration](https://docs.pingcap.com/tidb/stable/tidb-configuration-file/).

**Different clocks, not one timeout:** The TiDB DDL lease defaults to 45 s; the PD embedded-etcd election interval defaults to 3 s; TiKV's Region Raft election is about 10 s at its default ticks; TiKV's peer-down timer defaults to 10 min; and PD's disconnected-store replacement timer defaults to 30 min. The experiment's *client request* SLO is 5 s. These clocks describe different mechanisms and none alone proves the duration of a client-visible PD failover or the exact replica repair start. TiDB's PD-client request timeout is 3 s but does not specify a complete TSO outage/retry budget.

## What our deployment actually showed

- The *current checkout* (`powder/deploy/spec.py:111-140`, `powder/deploy/topology.py:54-89`) has separate three-member PD servers and user-data TiKV slots. The live `exec07-g1-live` worktree additionally pins system keys and `mysql.*` Regions to three dedicated, normally unfaulted `systikv` stores using a default PD rule, while an overriding rule places the experiment's user-table key range on fault-injected stores (`.claude/worktrees/exec07-g1-live/powder/deploy/placement.py:1-16,40-58`, `install.py:160-190`). These rules are not in the current branch. System Regions still share *region outages* with other components.
- The pre-pinning G3 run's TiDB logs contain `2pc.go` and `session.go` failures on `powder.kv` writes with `[domain:8027] Information schema is out of date: schema failed to update in 1 lease`, beginning near 2026-11-05 00:34:20 UTC in more than one TiDB server (`~/powder-runs/tidb/VividHawk/experiments/selftest-20261105T002619Z/logs/tidb-us-east-2-1/tidb-4000/log/tidb.log:86154-86160`; another TiDB log in the same run has the same error near `:73223-73229`). The archived fault timeline shows the first two TiKV stops applied at 00:33:21 UTC and their restarts at 00:34:21 UTC (`faults/applied.jsonl:1-4`); the first observed 8027 at 00:34:20 is roughly 59 s after the stop, just before restart. The live branch's placement note reports that loss of voters in system Regions including `tidb_mdl_info` / `tidb_background_subtask` coincided with cross-table write failures. This is concrete evidence of the schema-check failure mode **in that run**, not proof that *every* `mysql.*` table's loss, without a schema-path failure, stops *every* write after exactly 45 s.
- The subsequent dedicated-system-store gate (`FluffyTiger`) was intended to isolate measured user-RSM failures from control-plane artifacts. Its deployment placement rule and the workload's request/probe outcomes should be kept separate when fitting a full TiDB model. No new billable run is authorized by this note.

## What the current model does and does not measure

The Python Raft predicate (`powder/simulation/protocol.py:485-505`) and Rust equivalent (`rust/powder-mc/src/sim/protocol.rs:557-572`) test **one user-data RSM**. The Rust MC job contains one cluster and strategy (`rust/powder-mc/src/config.rs:303-435`), not a jointly failed PD quorum, system-metadata Regions or TiDB frontends. The original MC metrics accumulated total unavailable seconds and incident count; optional episode timing now supplies the missing thresholded durations (`rust/powder-mc/src/sim/metrics.rs`, `rust/powder-mc/src/job.rs`). Neither the original total nor incident count alone suffices to calculate time beyond a threshold.

The live load generator uses a **5 s per-request SLO**; its periodic probe does a write *and* read, so a mixed probe timeout is not a write-only failure (`infra/tidb/loadgen/main.go:287-350`; live branch has an additional KILL QUERY policy). Current summaries report timed-out requests and probe-bin fractions, not contiguous write-outage episode lengths (`powder/deploy/availability.py:178-293`). `pd_cluster_status` samples in the fixture describe TiKV store/Region counts, not PD-member quorum. An unavailable client probe bin is not itself proof of a PD or system-table outage.

## Metric and model extension

**Phase 1: measure before changing the availability claim.** For every maximal write-unavailable episode of length `d` in a fixed-horizon MC run, expose `count(d > T)`, `max(d)`, total unavailable seconds `sum(d)`, and *post-threshold tail* `sum(max(d - T, 0))` for caller-supplied `T` in seconds. Also report `sum(d * 1[d > T])` separately if the experiment wants to classify **entire** long incidents; these are not the same statistic. Carry open episodes through the fixed-horizon flush and mark end-censored episodes; keep `stop_on_data_loss=false` when estimating time fractions. Test episodes below, at, and above T, multiple outages, start/end censoring, and zero T. Add this pure timing statistic to Rust metrics, per-run job records and summaries, with the Python bridge exposing it; preserve old fields and behavior when T is unset. The existing node-replacement `failure_timeout` is not T.

**Interpretation of T matters.** A 45 s schema freshness lease is a *grace after the last successful refresh*, not necessarily 45 s after the fault begins: the refresh phase at outage onset may vary. A 5 s client deadline measures whether an operation **started at time t** finishes within five seconds. In an ideal no-retry service outage `[a,b)`, the failed request-start interval is `[a,b-5s)` (length `max(b-a-5s,0)`), while a 45 s schema-expiry gate affects the *tail* `[last_refresh+45s,b)`. They can have the same length for one isolated episode yet different overlap with user-RSM faults. Do not relabel a long user-RSM outage as a schema failure merely because it exceeded 45 s.

**Phase 2: simulate the missing joint dependencies.** In a shared event timeline, add PD membership/TSO reachability, distinct system-store and schema-metadata Regions, and TiDB-server schema-freshness clocks. Reuse the **same region-outage events** across control-plane and user-data hosts; share physical hosts when they really are shared. For **new normal transactions**, gate user-shard writes on `(user Region committable) AND (reachable TSO) AND (schema valid on chosen TiDB server) AND (frontend reachable)`. An already-started causal-consistency 1PC transaction may commit without a fresh PD timestamp while schema remains valid (local test below); model that path separately rather than asserting all writes stop instantly. When PD scheduling is unavailable, pause repair/re-replication rather than setting every Region down. Compute the **union** of unavailable intervals per shard/request; never multiply independent marginal availabilities or add raw outage totals (overlap would double-count failures). Report user-RSM-only vs control-plane-only vs overlapping seconds and resulting end-to-end expected write availability. Keep the SQL/frontend gate conditional on measured workload assumptions.

**Phase 3: calibrate before claiming a TiDB correction.** Collect PD `/members` leader/quorum and TSO request failures; map PD Region snapshots for `m_` metadata and `mysql.*` system ranges separately from `powder.kv`; capture `8027`, `9001` and write-only request/probe outcomes with timestamps. Compare pre-pinning G3 and pinned-system-store cases offline, then run a **small, authorized** PD-failover and metadata-Region-fault experiment only if the existing logs cannot identify failure/recovery delays. Fit distributions for effective PD/TSO interruption, last-successful-schema-refresh to 8027, and scheduler repair delay. Do not assume the documentation's defaults are measured write-outage durations.

**Until Phase 2 is validated,** a thresholded per-RSM statistic is a useful sensitivity measure, not a TiDB-wide write-availability correction. The reported paper metric must state whether it is *mean per-partition availability*, *all-shards-writable availability*, or *request success within the 5 s SLO*; these have different values even with the same underlying events.

- [x] Phase 1: optional `run.episode_threshold_seconds` in fixed-horizon Rust MC jobs (and `episode_threshold_seconds=` in the Python bridge); omitted for legacy jobs. Per-run and summary outputs report strict count `d > T`, unavailable time, largest episode, post-threshold tail, whole-duration long-episode time, and initial/end censoring. The existing Raft availability calculation is unchanged. Python callers must use `max_time` and `stop_on_data_loss=False`. The original replacement timeout remains separate.
- [x] Unit/integration validation: 205 Rust library tests, the focused Rust timing/availability suites, and 68 Python MC/deployment tests passed. The release engine rebuilt and returned the new summary through the Python API. The full Rust suite was attempted but stopped after approximately six minutes while three unrelated stratified tests were still running; it was **not** certified as a full-suite pass. No AWS deployment was run.
- [~] Phase 2 has an opt-in **deterministic/no-repair** whole-fleet replay pilot and scenario-coupled ILP (`docs/plans/tidb-composed-availability.md`). It still lacks a calibrated stochastic TiDB control-plane/Raft/repair model and Phase 3 live validation. Do not present the single-RSM `post_threshold_seconds` or pilot's composed value as paper-ready TiDB write availability.

## Local request experiment: PD unavailable (2026-11-11)

`infra/tidb/local_pd_dependency_check.py` ran the pinned TiDB/TiKV/PD v8.5.8 binaries in an off-cloud TiUP playground: **one PD, three TiKV, one TiDB**, a fresh table, SQL sessions established while PD was healthy, and a **5 s client read deadline**. It suspended only the tagged PD process with SIGSTOP for 76.02 s, then resumed it and stopped the whole playground in `finally`. PD `/health` succeeded before/after and timed out at the beginning and 60 s into the pause. Raw per-request evidence (baseline, outage, recovery, timestamps and responses): `outputs/tidb/local-pd-dependency-20261111.json` (ignored by git); the probe script and TiDB log under `~/.cache/powder/tiup-home/data/powderpdcheck3348331/tidb-0/tidb.log` are local. **Every SQL baseline and post-recovery request succeeded.**

| SQL request with PD paused | Observed within 5 s |
|---|---|
| `SELECT 1` on existing and new connections; `SHOW TABLES`; primary-key point get | Succeeded, including checks after 60 s. This does not establish that all `SELECT`s are independent of PD. |
| Fresh `SELECT SUM(v)` table scan | Timed out at 0, 11 and 61 s after PD stop. |
| Point get or full scan with a preselected `AS OF TIMESTAMP` | Succeeded, including a scan after 60 s; it returned the older snapshot, not current data. |
| `SELECT SUM(v)` with `tidb_low_resolution_tso=ON` | Succeeded at 1, 11 and 61 s, returning a cached snapshot. Do not assume it remains valid indefinitely. |
| New autocommit `UPDATE` | Timed out at 6 and 66 s after PD stop. A timed-out request does not by itself prove that TiDB rolled its transaction back. |
| `UPDATE` inside a transaction begun before PD stop | Statement succeeded; ordinary `COMMIT` timed out. Explicit healthy 2PC, 1PC-eligible and async-eligible transactions (verified as `2pc`, `1pc` and `async_commit` via `@@tidb_last_txn_info`) all had 5 s commit timeouts while PD was paused. |
| `START TRANSACTION WITH CAUSAL CONSISTENCY ONLY` with both 1PC/async enabled, begun before PD stop | `COMMIT` **succeeded** about 36 s into the pause and reported actual mode `1pc`. A second prestarted transaction's `COMMIT` at 71 s timed out; its TiDB log recorded schema error 8027 when processed. This is an exception to a blanket “PD down ⇒ every write fails immediately,” not evidence that new transactions can start without PD. |

Client timeouts were PyMySQL error 2013 after 5 s, not SQL error 9001; TiDB also logged `wait tso failed` during the outage, and error 8027 for the late causal transaction. This is a *single-PD full outage* rather than the production **three-member PD quorum** or a geographically correlated fault. It measures client-visible outcomes under these settings, not the probability of each request succeeding in a future deployment. The next calibration experiment should distinguish TSO unreachability from PD leader failover with a 3-member local cluster, and record whether timed-out commits eventually apply after PD resumes.
