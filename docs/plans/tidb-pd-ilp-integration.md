# Plan: PD-driven Powder placement for repair, split, and merge

Status: implementation in progress 2026-11-13; offline repair prototype only. Scope: October Goals 1.2, 1.4, and execution item 9. This is an opt-in change to the pinned PD v8.5.8 control plane, not a change to TiKV's Raft protocol or an AWS deployment authorization. It builds on `docs/plans/exec-07-tidb-deployment.md` §6.2/§8 and leaves the in-progress composed-availability and transition-cost work untouched.

## 0. Decisions and the important distinction

- **Yes, PD chooses the destination TiKV *store* for a missing/down Region peer.** With placement rules enabled, the Region patrol's `RuleChecker` uses `ReplicaStrategy.SelectStoreToAdd` / `SelectStoreToFix` to filter and rank stores, then constructs a safe add/move operator. The default rule is three voters. PD does **not** provision a new machine, and a lost Region leader is elected by TiKV/Raft rather than selected by this replacement oracle. A Region without a live leader cannot be repaired by PD until leadership/heartbeats recover. See `third_party/pd/pkg/schedule/checker/checker_controller.go:281`, `rule_checker.go:93-233`, and `replica_strategy.go:43-111`.
- **A store failure is many Region-level repairs.** For each affected Region, fix all healthy peers and their roles, choose *one* eligible replacement store for the missing peer, and leave every other Region's assignment untouched. Do not interpret “one replacement” as forcing all peers formerly on a failed physical store onto one successor: that would require an explicit spare and fleet-wide capacity planning. Administrative store removal, store heartbeat timeout, and Raft leader election are different events.
- **A split does not initially place children on new stores.** TiKV can initiate it; PD can request one at a rule boundary or through split/scatter APIs. PD allocates new peer IDs corresponding to the parent's peers, so children initially inherit its store set (`server/cluster/cluster_worker.go:75-193`). Ask Powder for *post-split* child placements after the new Region IDs/epochs are observable. Do not delay split ID allocation or TiKV's split on an ILP call. Split-scatter is not automatic in every configuration (its schedule-limit default is zero).
- **A merge does make a placement choice.** PD's merge checker chooses an eligible adjacent target, and `CreateMergeRegionOperator` first aligns source peers/roles/witnesses to the target before the merge (`checker/merge_checker.go:77-229`, `operator/create_operator.go:178-220`). Ask Powder which feasible adjacent direction/target store set to use **before** constructing the merge operators, without relaxing adjacency, key-range/rule compatibility, health, size, hotness or cooldown checks.
- **No full-fleet solve in the PD heartbeat/repair critical path.** The current `solve_transition_gurobi` builds a named-shard, whole-fleet assignment with coupled machine capacity, budget and optional aggregate move limits (`powder/faults/gurobi_ilp.py:100-305`); `max_replica_moves=1` does not turn it into an isolated single-peer solver. Some fleet solves hit their 120-second limit, and online single-replacement latency has not been measured. The repair oracle should enumerate the already-eligible stores and choose the best one (an exact, tiny constrained optimization); the existing ILP can prepare/cache policy and solve fleet-level reconfiguration asynchronously. No Gurobi license is needed in PD.

## 1. Ownership and event flow

| Event | PD/TiKV remains responsible for | Powder decides | Timing and bound |
|---|---|---|---|
| Missing, down, or administratively offline peer | Recognize the event under existing rules/timeouts; filter healthy/capable stores; create and throttle safe peer-add/promote/remove operators | Rank feasible destinations for **one** replacement peer of this Region, with remaining peers fixed | On the `RuleChecker` repair path; one bounded request, native ranking on timeout/error |
| TiKV- or PD-initiated split | Select/execute split keys, allocate IDs, preserve initial replica set | Placement of each confirmed child, initially allowing unchanged or at most one peer move per child | After split is reported; reconcile from Region ID, key range and epoch; never hold up the split |
| PD-initiated merge | Decide whether an adjacent pair is eligible; construct and dispatch paired merge operators | Among eligible source→target directions, rank survivor peer sets and the required alignment cost | Before merge operator creation; if alignment cannot be scheduled safely, defer merge |
| Normal balancing/scatter | PD retains hard safety and operator limits | Optional later integration: rank their destinations under the *same* policy | Explicitly scoped; do not claim that a `ReplicaStrategy` hook alone controls all moves |

Repair eligibility is not determined by a single configurable timer: PD's `max-store-down-time` and TiKV's `raftstore.max-peer-down-duration` are separate gates. The local v8.5.8 observation with PD set to one minute still started replacement about nine minutes after killing a store (`infra/tidb/README.md:68-71`). These gates are not client-outage durations. A physically lost store requires a separately provisioned eligible TiKV store (TiUP scale-out or an already-available spare); PD merely places Region peers.

## 2. Interface and safety contract

1. Define a versioned, read-only `RecommendPlacement` request/response between the forked PD and a small `powder-oracle` process. Request includes event kind, request/model versions, Region IDs/key ranges/epochs and approximate sizes, present/down/pending peers and roles/witness flags, eligible target store IDs with `region`/`zone`/`host`/`machine_class`, store-state/capacity and placement-rule identifiers, and any movement/decision budget. Split and merge requests include both child or neighboring Region identities. Response returns the chosen eligible store/merge direction or `defer`, a score and reason; it does **not** return arbitrary executable PD commands. A missing/stale feature must yield `defer` or native fallback, not a fabricated score.
2. Put Powder's objective behind this API, independent of PD's Go code. Start with a deterministic table/cache of precomputed placement scores for the pinned fault/model version, with a documented cheap local scoring path if cache coverage and latency permit. For a one-peer repair, enumerate `P - {failed} + {candidate}` over PD's feasible candidates, price one new replica's storage/snapshot transfer and compare availability/cost under a fixed objective and tie-break. Count capacity and outstanding moves across concurrent repairs, not just inside one Region. Until joint TiDB availability is calibrated, call this a per-Region placement surrogate, not a certified whole-system write-availability optimum. Keep `powder/faults/gurobi_ilp.py` for asynchronous, coupled fleet plans; use its selected assignments as advice only after mapping actual Region/store identities and revalidating current state.
3. Preserve PD's placement rules (including learner/voter/leader/follower and witness), replica count, hard location isolation, store-state/capacity/snapshot filters, pending-peer and active-operator checks, plus per-store and replica/region/merge schedule limits. Integrate *after* PD computes eligible candidates, never bypass the operator builder: it adds a learner, promotes when appropriate, transfers leadership if needed, and removes the old peer safely (`checker/replica_strategy.go:43-132`, `operator/builder.go:583-645`). Recheck Region epoch, peer set, target store and rule fit just before committing an operator; an old reply must not move peers of a newly split/merged Region.
4. Make the oracle optional and fail open to **PD's normal safe store ranking** for repair on connection failure, timeout, malformed result, stale cache or invalid candidate. A merge or discretionary post-split move can instead defer: it must not block urgent repairs. Bound request time and concurrency, cache decisions by versioned Region/peer/eligible-set state, emit latency and fallback reasons, and ensure no external solver is needed for PD leader election or heartbeat processing. Benchmark the timeout before setting it; do not assume the full ILP's solve time is acceptable. Use a loopback or explicitly secured endpoint on each PD host; the reserved `ORACLE_PORT=8650` and parsed `oracle.enabled` are not yet a deployed oracle (`powder/deploy/netplan.py:19`, `powder/deploy/spec.py:140,210`). Verify network and service wiring rather than relying on the old plan's placeholder description.
5. Scope authority across schedulers. A repair hook alone does not govern `balance-region`, hot-region moves, split-scatter or explicit scatter. Initially disable/confine conflicting *discretionary* moves in Powder-vs-baseline experiments, or route only those intended to be Powder-controlled through the same candidate policy; keep safety repair and leader handling active. Log the decision origin and resulting PD operator so a later unrelated scheduler cannot be misattributed to the ILP. PD placement-rule APIs can enforce coarse role/label constraints without a fork, but cannot express a per-Region, dynamically ranked exact store choice by themselves.

## 3. Implementation sequence and acceptance gates

**A. Contract and reference oracle (no PD patch).** Add a pure Python request validator/ranker in `powder/deploy/` with versioned JSON fixtures and a small service entry point in `infra/tidb/`. Reuse physical store IDs and machine labels from `powder/deploy/topology.py` and `powder/deploy/regionmap.py`; map `RegionInfo` to a named shard and Region size to storage/movement GB, distinguishing estimated size from measured snapshot bytes. Enumerate replacement candidates and test unchanged peers, full/near-full stores, rule roles, region isolation, ties, stale epochs, missing model data and two repairs competing for capacity. Acceptance: every returned destination is in PD's feasible input set, zero or one replacement per Region, deterministic output and an explicit fallback for every unsupported input. Keep a local score oracle usable without a Gurobi license.

**B. Opt-in failure repair.** Patch the pinned `third_party/pd` submodule at the rule-enabled `ReplicaStrategy.SelectStoreToAdd/SelectStoreToFix` decision point (and cover the rules-disabled legacy path only if experiments use it); provide a Go oracle client and an injectable interface for tests. Do not replace PD's eligibility filters or conf-change builder. Wire the optional service/config into `powder/deploy/spec.py`, `powder/deploy/netplan.py`, install/health checks and manifests; build and patch only PD through TiUP as described in `docs/plans/exec-07-tidb-deployment.md:349-353`. Acceptance: PD unit tests with fake oracle cover valid, invalid, slow, down and stale responses; with oracle off, store choice/operators match stock PD. In a local TiUP cluster with at least four eligible TiKV stores for an RF=3 Region (the three-store playground has no spare), kill one TiKV store, wait for the configured PD **and** TiKV reporting gates, and show exactly one replacement per affected Region with unaffected peer IDs/stores unchanged; also check learner promotion/operator completion and native fallback. A total Raft quorum loss must not be reported as a successfully repaired Region.

**C. Post-split placement.** Observe confirmed splits in PD's checker/heartbeat flow and queue an idempotent, epoch-checked child-placement decision (plus explicit split/scatter paths as needed). Initially restrict each child to zero or one peer replacement; the parent/other children need not change. Use normal move-peer operators, throttles and capacity reservations. Acceptance: force TiKV-originated and PD/API-originated splits locally; neither waits on the oracle, children first inherit parent stores, desired moves complete safely, retries or repeated heartbeats do not duplicate moves, and disabled/default split-scatter is not mistaken for successful Powder placement.

**D. Merge placement.** In `MergeChecker.Check`, compare only PD-eligible adjacent targets and feasible survivor placements. First implementation selects one existing side's compatible store/role set, scores its required source alignment and has `CreateMergeRegionOperator` perform that alignment; a third store set would require explicit staged moves of both sides and is deferred. Preserve split/merge cooldown and reject different applicable placement rules. Acceptance: local tests cover both merge directions, unequal peer sets/roles, insufficient capacity, concurrent operator, cooldown and failed oracle; verify the final Region's stores equal the selected survivor and no merge is forced when alignment fails.

**E. Measurement and opt-in experiments.** Log `{event, region/epoch, old and proposed peers, eligible set, model version, score/cost, oracle latency, fallback reason, PD operator IDs, observed completion, bytes moved}` without blocking scheduling on logging. Extend `powder/deploy/experiment.py` / Region-map attribution to compare stock PD, policy-off fork and policy-on fork for repair/split/merge operator counts, capacity violations, recovery delay, moved GB, availability and request latency. Confirm PD member/TSO and system-Region behavior independently; the local single-PD pause described in `docs/plans/tidb-write-availability-dependencies.md` does not calibrate three-PD failover or joint write availability. Benchmark oracle p50/p95/p99 and fallback rate under realistic Region counts before an AWS experiment. **No billable deployment or fault injection without explicit approval.**

## 4. Deferred work and non-blocking choices

- Initial ILP-generated TiDB `spec.yaml` (October Goal 1.2.1), exact per-store storage-GB accounting and GB-movement budgets, whole-fleet asynchronous reoptimization, and calibrated composed PD/metadata/user-Region availability are separate follow-ups. The current fleet solver uses replica-slot capacities and optional aggregate replica additions, not a complete physical disk/snapshot or online scheduler model. The uncommitted composed-availability work must not silently become a prerequisite for safe single-peer repair.
- Decide whether to reserve a hot spare, how much cross-region snapshot bandwidth/GB movement to budget, and whether planned repairs may trade away existing isolation **before** relaxing the initial fixed-peers/one-move policy. Missing capacity should cause `defer`/native handling, not a global reshuffle disguised as single-peer replacement.
- Keep a reproducible baseline: pinned `third_party/tidb/VERSIONS`, pinned PD source, model/library version, input Region map and enabled-scheduler/config snapshot in each run. Changes to the PD submodule are separately reviewed/tested; do not alter the baseline tag in place.
